# О работе над Mini CRM API

Самая сложная часть решения - одновременное назначение встреч: два запроса могут увидеть один слот свободным.
Поэтому проверка занятости и запись защищены одной транзакцией, а одинаковые правила применяются при создании и переносе.

С учётом ограничения в четыре часа для хранения выбран SQLite, которому не нужен отдельный сервер.
История ограничена первоначальным временем встречи и временем создания записи, без отдельного журнала каждого переноса.
Дополнительная инфраструктура не добавлялась, чтобы сохранить небольшой объём кода и понятный запуск.

При дополнительных восьми часах первым шагом стала бы проверка конкурентной нагрузки с несколькими процессами и большим числом встреч.
По результатам этой проверки можно было бы оценить переход на PostgreSQL с ограничениями пересечений на уровне базы.

Codex использовался для реализации кода, тестов и документации.
В ходе работы уточнялись требования к простоте функций, защите конкурентных операций и содержательности тестов.
Аудит не выявил ошибок в коде приложения, но показал, что часть тестов проверяла только код ответа или неполное состояние данных.
Эти проверки были усилены, а отдельный тест подтвердил откат звонка при ошибке обновления статуса организации.

Неоднозначным оказалось требование о двух активных встречах одной организации.
Оно трактуется как запрет пересекающихся интервалов, в том числе у разных менеджеров; встречи организации в разное время разрешены.

## Два одновременных назначения

Если два запроса претендуют на пересекающиеся встречи одного менеджера или одной организации, перед чтением слотов каждый выполняет `BEGIN IMMEDIATE`.
SQLite допускает одну транзакцию записи одновременно, поэтому второй запрос ждёт завершения первого.
После получения блокировки второй запрос заново читает занятость слота и проверяет её по актуальным данным.
Если первый запрос уже занял этот слот, второй получает HTTP 409; если блокировка не освободилась за пять секунд, возвращается HTTP 503 с предложением повторить запрос.
Для переноса действует та же защита, а встречи разных организаций у разных менеджеров в одно время разрешены.
Тесты с двумя отдельными соединениями к одному файлу SQLite проверяют конкурентное создание и перенос: целевой слот занимает только один запрос.
Если под нагрузкой дубли всё же появятся, сначала нужно воспроизвести случай и проверить, что все записи проходят через защищённую транзакцию и используют одну базу.
При серьёзной нагрузке потребуется пересмотреть стратегию конкурентного доступа и рассмотреть PostgreSQL с ограничениями пересечений на уровне БД, затем повторить нагрузочную проверку.
