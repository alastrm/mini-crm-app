# Mini CRM

REST API для учёта звонков организациям и встреч с менеджерами.
Python 3.12+, FastAPI, Pydantic и встроенный SQLite. Интерфейс не требуется.
Проверено на Python 3.12.10; версии зависимостей закреплены в `requirements.txt`.

Готовы все шесть маршрутов, валидация, рабочие часы, проверки пересечений
и защита конкурентного бронирования. Есть схема БД, два тестовых менеджера
с ID `1` и `2`, документация `/docs`. Примеры HTTP-запросов и итоговый
`REFLECTION.md` будут добавлены позже. Документация ещё не завершена.

## Установка и запуск

Откройте терминал в папке проекта. Нужен установленный Python 3.12 или новее.
Зависимости устанавливаются в отдельное окружение; активировать его не нужно.

Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app
```

Linux / macOS:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn app.main:app
```

После установки для запуска нужна только последняя команда.
Документация API: <http://127.0.0.1:8000/docs>.
Для остановки нажмите `Ctrl+C`.

## База данных

При запуске приложение выполняет `schema.sql`. Таблицы создаются только
при отсутствии, существующие данные сохраняются. Менеджеры добавляются
только при отсутствии их ID.

- `companies`: название, уникальный БИН из 12 цифр, телефон, статус.
- `managers`: два тестовых менеджера.
- `meetings`: организация, менеджер, текущее и первоначальное время встречи,
  время создания записи, статус.
- `calls`: организация, результат звонка, связанная встреча, время записи.

`CRM_DB_PATH` задаёт путь к SQLite-файлу. По умолчанию это `crm.sqlite3`
в текущей папке. Если указываете вложенную папку, создайте её заранее.
Пример для PowerShell перед запуском:

```powershell
$env:CRM_DB_PATH = "local.sqlite3"
```

Пример для Linux / macOS:

```bash
export CRM_DB_PATH="local.sqlite3"
```

Соединение включает проверку внешних ключей и ждёт освобождения занятой БД
до 5 секунд. Файлы базы исключены из Git.

## Проверки

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Linux / macOS:

```bash
.venv/bin/python -m pytest -q
```

Тесты проверяют запуск, сохранение данных после перезапуска, создание
организаций, пагинацию, валидацию, повторный БИН, запись звонков и сохранение
SQL-текста как обычных данных. Каждый тест использует отдельный временный файл БД
и не меняет рабочую базу. Также проверяются создание, перенос и отмена встреч,
связь звонка со встречей, UTC-ввод, расписание и ошибки `404`/`422`.
В `tests/test_rules.py` проверяются границы рабочего дня, выходные, пересечения
менеджера и организации, смежные встречи, перенос на занятое время,
освобождение отменённого слота и местные границы дня для расписания.
Конкурентные тесты запускают два HTTP-запроса через TestClient, каждый
с отдельным настоящим SQLite-соединением к одному временному файлу БД.
Проверяются и создание, и перенос: ровно один запрос занимает общий слот.
Тест занятой БД действительно удерживает блокировку дольше 5 секунд,
проверяет `503`, затем освобождает её и повторяет запрос успешно.

Установленная версия Starlette выводит предупреждение о будущем отказе
от `httpx` в `TestClient`. Тесты проходят; предупреждение не скрыто.

## Организации

`POST /companies` принимает `name`, `bin` и `phone`. БИН — строка из 12 цифр;
начальные нули сохраняются. Название и телефон не могут быть пустыми.
Пробелы по краям строк удаляются. Формат телефона дополнительно не ограничен.
Создание возвращает `201`, повторный БИН — `409`, неверные данные — `422`.

`GET /companies` возвращает `items`, `total`, `page`, `page_size`.
Параметр `status` необязателен: `new`, `no_answer`, `refused`, `meeting_set`.
Страница начинается с `1`, размер по умолчанию `20`, максимум `100`.
Номер страницы ограничен сверху, чтобы SQL-смещение помещалось в число SQLite.
Организации отсортированы по ID. Новая организация имеет статус `new`.

## Звонки

`POST /calls` принимает `company_id`, `result` и необязательный `meeting_id`.
Результат: `no_answer`, `refused` или `meeting_set`.
Для `meeting_set` нужна существующая активная встреча той же организации;
для остальных результатов `meeting_id` нужно опустить или передать `null`.
Отсутствующая организация даёт `404`, неверная связь со встречей — `422`.

Наш выбор: статус организации отражает последний результат звонка.
Звонок и новый статус сохраняются одной транзакцией. Отказ от встречи
не отменяет уже назначенную встречу автоматически.

## Встречи и расписание

`POST /meetings` принимает `company_id`, `manager_id`, `start_at`.
ID должны быть положительными целыми числами в диапазоне SQLite;
неизвестная организация или менеджер дают `404`. Создание возвращает `201`.
Пример времени: `2026-11-23T05:00:00Z` — 10:00 в Asia/Almaty.
Принимаются UTC ISO 8601 со смещением `Z` или `+00:00`; время без зоны,
другое смещение и числовой Unix timestamp отвергаются с `422`.
Ответы возвращают время в UTC.

`PATCH /meetings/{id}` принимает ровно одно действие:

- `{"start_at": "2026-11-23T06:00:00Z"}` — перенос;
- `{"status": "cancelled"}` — отмена.

Пустое тело, `null` вместо действия, оба действия одновременно и другие поля
дают `422`. Неизвестная встреча даёт `404`. Отменённую встречу нельзя перенести
(`409`); повторная отмена возвращает `200`.

Встреча возвращает `id`, `company_id`, `manager_id`, `start_at`,
`original_start_at`, `created_at`, `status`. Перенос меняет только `start_at`;
первоначальное время и время создания записи сохраняются. Это наш выбор
трактовки истории: промежуточные переносы отдельно не записываются.

`GET /managers/{id}/schedule?date=2026-11-23` возвращает список активных
встреч менеджера, отсортированный по началу. `date` — календарный день
Asia/Almaty, а время в ответе остаётся в UTC. Нужна действительная дата
в формате `YYYY-MM-DD`, без неё — `422`. Неизвестный менеджер даёт `404`.
Наш выбор: отменённые встречи в расписании не показываются.

## Рабочие часы и пересечения

Встреча всегда длится 60 минут. Сервер переводит начало и конец из UTC
в Asia/Almaty и разрешает только пн–пт, 09:00–18:00. Весь интервал должен
лежать в одном рабочем дне: 09:00 и 17:00 допустимы, 17:30 — уже нет (`422`).
Создание и перенос используют одни и те же функции в `app/rules.py`.

Пересечение определяется так:
`existing_start < new_end and new_start < existing_end`.
Поэтому 10:00–11:00 и 11:00–12:00 разрешены, а 10:00–11:00 и 10:30–11:30
конфликтуют (`409`). Проверяются и менеджер, и организация, в том числе
при разных менеджерах. Отменённые встречи не учитываются; при переносе
сама переносимая запись исключается из проверки.

## Одновременные запросы

Создание и изменение встречи начинают `BEGIN IMMEDIATE` до чтения данных.
Получение блокировки, проверка занятости и INSERT/UPDATE находятся
в одной транзакции на одном соединении. После успеха `with connection`
выполняет COMMIT, а при ошибке — ROLLBACK.

Если два запроса претендуют на конфликтующий слот, первый записывает встречу,
второй ждёт, затем проверяет уже обновлённые данные и получает `409`.
Если блокировка не освобождается за 5 секунд, ответ — `503` с понятным
сообщением и `Retry-After: 1`. Это временная занятость БД; запрос можно повторить.
Такая же транзакция используется для звонков, чтобы встречу не отменили
между проверкой `meeting_set` и записью звонка.

SQLite допускает одного писателя одновременно, в том числе для разных
свободных слотов. Это приемлемо для тестового проекта; решение не проверено
под большой нагрузкой и не заявляется заменой серверной БД в production.
